How a stage earns it

Every stage climbs the same ladder, on evidence

I wire in what I have one stage at a time. A stage gets more autonomy only when the run log shows it has earned it, and Merge climbs last.

StageLevel nowEarns the next level when
Intakelevel 0 · manualIt marks issues ready or not, and its lane; I agree on 9 of the last 10.
Planlevel 0 · manual9 of the last 10 plans approved without edits.
Buildlevel 0 · manual9 of the last 10 PRs merged with no rework.
Checklevel 0 · manualCatches every planted defect, and fails good work at most 1 in 10. Plus every planted defect caught.
Reviewlevel 0 · manualMy reviewer flags what I flagged on 9 of the last 10 PRs, and catches every planted defect. Plus every planted defect caught.
Mergelevel 0 · manualOnly once every other stage is at level 3. Then 10 merges that hold: none undone or fixed later.
The rules
  • A level counts only with evidence in the run log. No log, no level.
  • Climb on the last 10 real jobs, never on a good day.
  • Check and Review also need planted failures: known-bad changes they must catch, every one.
  • One serious miss drops the stage a level. Trust is lost faster than it is earned.
  • Merge climbs last, once every other stage is at level 3.
  • The thresholds are a starting point. The Friday review tunes them.

Draft designs

How four of the leanings would work

Drawn from where I am leaning on the cards above. They change if the decision does.

The review stack: who reads a PR before me

  1. Checks first. Nothing is reviewed until the e2e integration tests, lint and types pass, and the run has written what it checked.
  2. Claude’s review covers general coding practice.
  3. My reviewer knows this product: its CLAUDE.md, past decisions and history. It is strict on purpose, like the engineer who does not want the code to change.
  4. I read last, with both reviews in front of me. When I find something my reviewer missed, it becomes a new rule for it.

Risk lanes: where an issue goes

  1. Small and clear (a test, docs, a contained bug): straight to build.
  2. Ambiguous: the agent plans, and I approve the plan before any code is written.
  3. High risk (data, money, security, wide changes): stays out of the factory for now. I do it myself.

Where the fakes sit: AI calls in tests

  1. Engine swap, the p1 way: fast, free and the same every run, but my own AI code (prompts, reading replies, handling timeouts) never runs.
  2. aimock fakes only the model’s server, on my machine. My AI code runs on every push against scripted or recorded replies, including failures I cannot trigger on the real model.
  3. The live model runs now and then as a separate, paid tier, to check the model still judges the way the tests assume.

The sandbox boundary: what an unattended run can reach

  1. The agent and its copy of the repo live in a small VM. My Mac’s files, other projects, ~/.ssh and keys are not inside it.
  2. My API key stays outside. A proxy adds it to requests on the way out, so the agent never holds it and cannot leak it.
  3. Only allowlisted sites answer: Anthropic, GitHub, the package registry. Everything else is blocked.
  4. The GitHub token covers this repo only and can open PRs but not push to main.
Notes

The thinking behind some of the cards

Longer notes a decision card points to. They change if the decision does.

How big a run gets, and how I will know the agent is getting worse

suggested by Claude
  1. Why not wrap up mid-run. In my own sessions I wrap up when the context grows, because a squashed session loses detail. A factory moves that boundary to before the run: one issue fits one run, each stage (plan, build, merge) is its own run with a fresh context, and the state lives in files. The issue is the spec on disk, and fixed checks judge the result, so a forgetful or made-up answer is still caught before it merges.
  2. Size is already logged. Claude Code records the token count of every reply and marks each compaction. At the end of a run, the glue writes its peak context, its number of turns, and whether it compacted into the run note.
  3. The result, with no model judging. Checks passed first time or needed retries; I accepted the PR as it was, changed it, or rejected it; a test file was touched; the run hit its limit or compacted; the change was reverted or fixed again within a few weeks.
  4. Then compare. Size against result. If runs above some size fail or get rejected more often, that is my limit, and issues are split below it. The Friday review reads the trend.
  5. Known-answer issues. A few past issues with known good answers, re-run now and then, especially after a model update. If the same issue starts failing, the agent got worse, not my issues. Planted failures test the checks; these test the agent.

What an unattended run may write

suggested by Claude
  1. Two loops. My own sessions keep the handover, the backlog and wrap-up, so I pick up where I left off. Factory runs do not pass a handover from one run to the next.
  2. Every run starts clean. A fresh worktree and the issue as its brief. State carried between runs is drift.
  3. A run’s record is its issue, its PR and its run note. Time, cost, pass or fail, and any gaps it hit.
  4. Never memory or the handover. An issue can carry hidden instructions, and a run that saved them would make them reach every later session. Gaps go in the run note; I fill them in my own session, which matches the card on what context each run gets.

Things to watch

Where factories go wrong, and what I will do about it

  • Too many PRs to review · ReviewSmall issues, green checks first, a cap on open factory PRs.
  • Agents edit tests to pass · CheckE2E integration tests as the gate; lock the test folder; flag every test change in the PR.
  • The codebase slowly gets worse · MergeRead the code, not only the diff, in the Friday review. One team ran theirs lights-off from July 2025 and by November decided to rewrite from scratch.
  • Instructions hidden in issues · IntakeOnly issues I wrote or labelled ready are taken; no secrets in the run.
  • Tasks too big for one run · PlanSplit the issue. Raising the turn limit did not work for others.
  • Green runs that are wrong · CheckFresh worktree per run; prove each gate can fail with a planted defect.
  • Slow checks cancel fast PRs · CheckFast checks first, then only the tests a change affects, in parallel, from a database snapshot. Faster runners (StarSling) only if the run log shows CI waits.
  • An agent leaks a key · SafetyA sandbox, a GitHub token for this repo only that cannot push to main, no production keys anywhere a run can reach, and a network allowlist.
  • Cost creep · SafetySubscription first; a spend cap before any unattended run.
  • The factory costs more than it saves · MeThe Friday number. Two bad weeks in a row and I simplify.

Build your own software factory with Mastra Factory

Mastra’s CTO on what a software factory is, why review is the bottleneck, and the reviewer they built on top of CodeRabbit. Opinionated, and selling their own product in the second half, but the first 40 minutes are general advice.

For my factory

What this changes for me

  • Build a reviewer per project that knows the product’s intent, and run it after Claude Code’s own review. independent-reviewer is generic; this one would not be.
  • A run does not open a PR until its own checks pass: the 95% rule, applied to agents.
  • Three open decisions get an answer here: who merges (decided by evidence over time), keeping tests honest (e2e integration tests), and how small a task must be (risk lanes).

Review

  1. Run your own review agent on top of the generic one

    Generic bots (CodeRabbit, Greptile, Claude) check coding best practice. They do not know your product’s intent or behaviour. Theirs waits for CodeRabbit to finish, then adds its own view.

    “Having your own review agent on top of that is better because you can design your review agent as for example for us a [Mastra] maintainer. This agent knows about [Mastra] like that’s its whole job.”
    at 35:45 placed: card: who reviews before me

  2. Make it strict, and keep improving it

    Theirs is modelled on the senior engineer who does not want the code to change. It runs the tests and lints in a sandbox. By the speaker’s count only 40 of the PRs it reviewed were approved.

    “I wanted the review agent to be like that guy at the company who’s been there for 10 years who does not want the code to change.”
    at 53:07 placed: card: who reviews before me

  3. Get a PR to 95% confidence before opening it

    Throwing half-done work at reviewers deepens the bottleneck. He calls this the single most useful thing to do today.

    “We have this rule where you need to get your PR 95% confident before even opening it.”
    at 21:12 placed: card: when may a run open a PR

Trust and throughput

  1. A factory is earned in steps, not switched on

    Automate one loop, gather evidence (green tests, no incidents, clean releases), then remove a human gate. Repeat.

    “A software factory is a spectrum of ideas it’s not just you turn something on and you have it.”
    at 4:35 placed: the ladder, and card: what counts as evidence

  2. Review is the bottleneck

    Agents make PRs fast, but throughput counts end to end. A full review queue means more made and less shipped. The idea comes from The Goal, a book on factory bottlenecks.

    at 10:00 placed: card: how will I know it is worth it

  3. Long-term quality is the real test

    No benchmark measures whether agent code still stands three months later. Blindly accepting it is the maintainer’s trap.

    “You don’t want to get slop cannon.”
    at 18:24 placed: trap: the codebase slowly gets worse

Testing

  1. Prefer e2e integration tests to unit tests

    Models fake unit tests. E2E integration tests run end to end through how the system should and should not behave. Agents can write those too.

    “I think unit tests are a lie in this flow… because you could fake a unit test. Models love doing that.”
    at 23:30 placed: card: how do I keep the tests honest

  2. Mock the AI calls in tests

    They spent about $100 a day calling OpenAI from tests alone. AI mock (from CopilotKit) serves fixture data over HTTP instead.

    at 30:29 placed: card: how do I keep the tests honest

  3. Slow CI is a real cost

    A 16-minute CI wipes out a 5-second PR. They run only the tests a change affects and use faster runners.

    at 33:06 placed: trap: slow checks cancel fast PRs

Planning and routing

  1. Route work by risk

    Tests and docs: quick review. Ambiguous: lots of planning. High risk: a design review. Systemic: an experiment in a sandbox or staging.

    at 24:11 placed: card: how is work routed by risk

  2. Plan until you are sure enough to spend tokens

    “You plan until you get enough conviction that you want to spend tokens on it.”
    at 28:57 placed: card: how is work routed by risk

  3. Adversarial review yes, model councils no

    An agent that second-guesses everything is useful. Four models debating a plan mostly burns tokens.

    “Imagine an agent that just hates you and everything you say tries to like second guess you which I actually like.”
    at 38:41 placed: card: who reviews before me

Context and running it

  1. The issue text is not enough context

    Agents also need the git history of the area, a knowledge base, memory across sessions, and access to CI results and telemetry.

    “Why would you give them less tools than you have yourself?”
    at 25:39 placed: card: what context does each run get

  2. Agents report their own knowledge gaps

    When their agent does not know something, it opens an issue so a human can fill the gap. The knowledge base improves from use.

    at 59:34 placed: card: what context does each run get

  3. Measure the factory itself

    Queue health, what is coming in, agents running, cycle times, and cost per task.

    at 56:23 placed: card: how will I know it is worth it

The stack

  1. Factories need open, adaptable, code-defined infrastructure

    He treats the factory as an infrastructure stack, not a product or an AI teammate. Open means any model, open-weight or frontier, and any harness; adaptable means it works with your existing infrastructure.

    “the key aspects of this are like it should be open, it should be adaptable, and you should think of your factories as something that you define in code.”
    at 4:15 placed: card: can the factory switch agent tools and models

  2. Define the factory in code and version control it

    Workflows, skills, MCPs and where they run get a strict definition. In version control you can test versions of the factory, and coding agents can update it.

    “And when you define it in code and version control it, then you get the ability to like test different versions of your factory. You get the ability for coding agents to update your factory.”
    at 5:00 placed: already in the plan: skills, hooks and agents in git (`~/.claude`)

  3. A full factory platform is overkill for one person

    He says Warp’s platform works best for teams of about 10 or more engineers, and an individual would likely use a coding-agent subscription instead.

    “It is best for teams though I will say because like if you're if you're an it's just overkill for an individual. Like you're probably going to want to use like your cloud code sub or something.”
    at 21:38 placed: already in the plan: build my own, thin (part 1)

Runs and learning

  1. Store every agent run as raw material

    Warp records every engineer’s and automation’s agent runs, conversations and artefacts, as the material the factory improves from.

    “But the important thing here is that um all of this data is getting stored. And what your coding agents are doing is the raw material for improving that.”
    at 9:34 placed: idea: full run transcripts linked from the run log

  2. Agents group failures into patterns and propose factory fixes

    His self-improvement loop: agents collect failures, find patterns and suggest a change to the factory definition as a PR.

    “the idea behind a self-improvement loop is that agents will go and they'll look at all these failure modes. They'll aggregate them. They will look for patterns.”
    at 13:27 placed: idea: an agent drafts the Friday review

  3. Factory engineering is its own kind of engineering

    Product work goes through the factory; improving its skills, context and model mix is separate work.

    “But there's a second kind of engineering which I call factory engineering which is uh either uh your platform team or just your general engineers will have to get good at like trying to make the factory better.”
    at 7:21 placed: already in the plan: the Friday review

  4. Track cost per PR and the share spent on checking

    Warp measures cost per PR and how much of it goes on scoring and benchmarking, and teams budget from that.

    “we give people the tools to measure like what's your cost per PR, and then what percent of the cost is going towards like scoring or benchmarking or stuff like that.”

Models

  1. Choose models by replaying your own past tasks

    Public benchmarks do not tell you how a model does on your work. Warp replays real past tasks against model setups and plots cost against quality.

    “what what it does is it will replay your real past coding agent tasks and then generate for you what looks like a basically a cost versus quality trade-off graph.”
    at 16:10 placed: backlog row 9

  2. Build the first benchmark set by hand

    He recommends starting by hand, with a spread of small, medium and hard tasks.

    “you can either build up a benchmark set by hand, which a lot of people will do. They'll you know, and that's kind of what we recommend to start.”
    at 20:12 placed: backlog row 9

  3. Turn benchmark results into model routing

    His example: one model at 93% for $2 against another at 95% for three times the cost, on Warp’s own tasks.

    “you can take this information and then build a model routing strategy that you have real confidence is not just a generic one, but for your actual code, your stack, is actually providing value.”
    at 16:45 placed: backlog row 9

Review load

  1. Spec-driven development stops PRs piling up

    Automating development piles up PRs; his first advice is to check every change against a spec.

    “The big things that I advise are spec-driven development, so you could actually test um make sure that the changes are adherent to a spec.”
    at 18:21 placed: already in the plan: the Plan stage writes what done looks like

  2. Agents show evidence from the user’s side

    His second advice, not demoed: agents verify the feature as a user would and produce evidence, which cuts code review.

    “if you can have agents that verify or produce evidence from the user standpoint that the thing works, that can go a long way in terms of like lessening the code review burden.”
    at 18:37 placed: idea: product review with agent proof

  3. Scores catch known failure modes

    Online evals where an AI judge reviews runs, such as one looking for redundant tests. He says human grading also “makes total sense”.

    “And so for instance we have a score here that is looking for agents that are writing redundant tests which is a common failure mode with these coding agents.”
    at 12:43 placed: not taken as a gate: in Check a model never decides pass or fail
